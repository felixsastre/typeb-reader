# Changelog

Format: [Keep a Changelog](https://keepachangelog.com/). Every change of behaviour is listed under **Changed**, with the reason and the feature it comes from. Where a change is covered only by an internal Go test and by no scenario, the entry says so.

## [Unreleased]

### Changed

#### Third round (code review of the second round)

- `features/typeb_envelope.feature`, "A priority line that is not separated by exactly one space is rejected": the priority line is read strictly. Its fields must be separated by exactly one space, with no leading or trailing whitespace, no tab and no empty field; anything else is rejected on line 1, before the fields are checked, with the error `fields are separated by exactly one space, with no leading or trailing whitespace`. Reason: the line was split on any run of whitespace, so ` QU MADRMXA`, `QU  MADRMXA` and `QU<tab>MADRMXA` were accepted and read as if they were well formed.
- `features/typeb_envelope.feature`, "A carriage return that is not part of a line break is rejected" and "A carriage return in the middle of a line is rejected": only a line feed, or a carriage return followed by a line feed, ends a line. Exactly one carriage return is dropped, the one of a CRLF. Any other carriage return (a lone one at the end of the message, two before a line feed, one in the middle of a line, in the envelope or in the body) is never stripped: the line that holds it is rejected with `carriage return outside a line break` and its number. Reason: all trailing carriage returns of a line were stripped, so `AD0805/0812<CR><CR>` was accepted, and a carriage return inside a line was left to fail as an unrelated pattern mismatch.
- `features/typeb_envelope.feature`, "A date rule is skipped when one of its two dates is absent" and "A date rule still rejects an end before the start when both are given": a `not_before` rule applies only when both of its dates are present. Before, a missing date was read as the zero date, so a line with a start and no end was rejected with `date "" is before ...`. A date that is present is parsed and a parse failure is reported as an error with the line number, not ignored. The failure branch cannot be reached through a grammar, because the kinds are checked first; it has an internal test only.
- `features/typeb_envelope.feature`, "A first body line that is not exactly a message type is rejected": the message type is the whole first body line, matched exactly, and a line such as `MVT EXTRA` or `MVT ` fails on line 3 with `no grammar for message type`. The engine already behaved this way; the scenario pins it.
- `features/typeb_envelope.feature`, step `reading succeeds`: the accepted-case scenarios of this round check that reading did not fail and returned a message, not only the message type. A spec change with no change of behaviour.
- A grammar source with no `message` block is rejected, by `AddGrammar` and for the built-in grammars. Before, it was accepted and added nothing, so a typo such as `mesage "X"` failed silently. A load check; covered by an internal test only.
- `at_most_one` rejects a name listed more than once. Before, `["x", "x"]` loaded and then rejected every message that gave `x` once. A load check; covered by an internal test only.
- A zero `Reader` (`var r Reader`) works: `AddGrammar` creates the table it needs, and `Read` reports `no grammar for message type` for every type, because a zero Reader has no built-in grammars. Before, `AddGrammar` panicked. Covered by an internal test only; no scenario.
- `ReadSSM(nil)` and `ReadMVT(nil)`, and the same with a zero `Message`, return a `*ParseError` on line 1 instead of panicking. A message that was never read has no line of its own, so line 1 is the closest meaningful one. Covered by an internal test only; no scenario.
- `ReadMVT` returns the zero `MVT` whenever it returns an error, as `ReadSSM` returns the zero `SSM`. Before, it returned the half-filled value it had built. Covered by an internal test only; no scenario.

#### Second round (code review of the first version)

- `features/mvt_reading.feature`: MVT reads the forms found in public examples of the message, which the first version rejected. A departure or arrival can give one time (`AD0805`, `AD/0812`) or both, each time can carry its day (`AD210805/210812`), and these lines are read instead of rejected: estimates on the movement line (EO, RR, EA, EB), delays (DL), passengers (PX), estimated on-block (EB), leg day (FLD) and information (SI). Delay notices (ED, NI) are read too. Reason: the first version failed on the sample message in the IATA Type B whitepaper, which has a passenger line and a note. Lines of any other kind in an MVT are still rejected.
- `features/typeb_envelope.feature`, "A line that only contains the pattern is rejected": a line must match its grammar pattern from its first character to its last. A pattern written without `^` and `$` is matched against the whole line. Reason: such a pattern accepted lines that only contained it (`junk XA123 junk`).
- `features/typeb_envelope.feature`, "One line break at the end of a message is tolerated" and "Blank lines after the message are rejected": a message may end with one line break; any further break is a blank line and is rejected. Reason: every trailing break was dropped, so blank lines after a message were accepted.
- `features/mvt_reading.feature`, "The estimated on-block time can be on its own line" and "An estimated on-block time given twice is rejected": the estimated on-block time (EB) can be on its own line, and a message that gives it on the movement line and on its own line is rejected on the second line, even when the two times are equal. Reason: the reader used to pick the movement line and ignore the other without saying so. This comes with the grammar attribute `at_most_one`, a list of captures of which at most one may be given in the whole message. Its load checks, listed in `REFERENCE.md` under "The grammar format", are covered by internal tests only. `grammars/mvt.hcl` uses it for EB.
- `ReadSSM` and `ReadMVT` return a `*ParseError` with the line of the value that failed; when the message is of another type, the line is that of the message type (line 3). Reason: an error always carries the line number. Covered by an internal test only; no scenario.
- `Message.Value` skips groups that took no part in a match, so an optional group that did not match no longer hides a later value captured under the same name. Covered by an internal test only; no scenario.
- A grammar whose `when` names the capture `""` is rejected when it is loaded. Covered by an internal test only; no scenario.
- When a line breaks several `not_before` rules, the error reported is always the same (first in name order). Before, it depended on map order. Covered by an internal test only; no scenario.
- `ReadMVT` returns an error for a movement code that is not AD, AA, ED or NI. Before, any other code was read as a delay notice. Covered by an internal test only; no scenario.

#### First version

- `features/typeb_envelope.feature`: `Reader.Read` reads the envelope of a Type B message (priority, destination addresses, origin address and day, hour and minute of sending) and checks the body against the grammar of its type. Errors are `*ParseError` with the line number. Rejected with the line and the text: unknown priority, malformed address, impossible date, time or day, a line longer than 63 characters, an unknown kind of message and an envelope with no body.
- `features/ssm_reading.feature`: `ReadSSM` reads Standard Schedule Messages with the actions NEW, CNL, RPL and TIM, with period, days of operation, equipment and legs. Rejected: days of operation out of order, a period that ends before it starts, an unsupported action, a missing line and an unexpected line.
- `features/mvt_reading.feature`: `ReadMVT` reads Movement messages, departure (AD), arrival (AA) and delay notices (ED, NI).
- Grammar files (`grammars/*.hcl`) define the kinds of message, with the attribute `optional` and the kinds `moment` (hhmm or ddhhmm) and `duration` (hhmm). `Reader.AddGrammar` adds one at run time (scenario "A new kind of message is added with a grammar alone"). A grammar is checked when it is loaded (the checks are listed in `REFERENCE.md`); they have internal tests only.
